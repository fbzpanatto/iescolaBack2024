4. FAILURE-MODE ANALYSIS
(i) S3 move succeeds, UPDATE fails (DB blip, connection drop, process killed between Delete and UPDATE):
    - The original object is already deleted, DB still holds the legacy key -> 404 for students on that image.
    - Re-running the route does NOT heal it: HeadObject on the legacy key throws NotFound and the row lands
      in `falhas` again. Healing is a DB-only repoint (section 5), valid because questions/<key> exists.
    - The same happens if the Node process is restarted mid-run (deploy, pm2 restart, OOM).
(ii) Two rows sharing one key: currently 0 locally, so not expected. If production had one, the second row
    would fail with NotFound after the first row's Delete (first row ends correct, second keeps the legacy key
    and 404s) -> same section 5 repoint fixes it.
(iii) Duration / timeouts: strictly sequential, 3 S3 calls + 1 UPDATE per row, 553 rows -> ~2,212 round
    trips. At ~50-150 ms per S3 call from the AWS host, estimate ~1.5-4.5 minutes total (worse if the
    bucket region differs from the server). That exceeds the default nginx proxy_read_timeout (60 s) and the
    default ALB idle timeout (60 s). Likely outcome: the client gets 504/connection closed while the Node
    loop KEEPS RUNNING to completion (Express does not abort on client disconnect). The migration still
    finishes but the JSON with movidos/falhas is lost, so failures can only be inferred from the DB
    (rows still without '/') and from S3 HEAD checks.
    Do not retry the POST while the first run may still be executing (concurrent runs race on Delete and
    produce spurious NotFound entries; harmless to data but confusing).
Other observations:
- CopyObject uses MetadataDirective REPLACE without ServerSideEncryption/Metadata (aplicarNoCache passes
  them explicitly). Bucket default encryption (SSE-S3) should apply; not verifiable here (no S3 access).
  Public read comes from the bucket policy (canary-verified on 2026-10-07), so no ACL is lost.
- Idempotency: after a partial run, re-running only selects rows still without '/', so already-moved rows
  are skipped. Copy overwrites a pre-existing destination, so re-running is safe for rows whose original
  object still exists.

5. RECOVERY SQL (ready to run; replace the id list with the ids from `falhas` in the response)
-- 5.1 Inspect first (read-only):
SELECT qi.id, qi.s3Key, qi.active, b.s3Key AS backupKey
FROM question_image qi
LEFT JOIN question_image_backup_s3key b ON b.id = qi.id
WHERE qi.id IN (/* ids from falhas */) AND qi.s3Key NOT LIKE '%/%';

-- 5.2 Repoint rows whose original object was already moved/deleted:
UPDATE question_image
SET s3Key = CONCAT('questions/', s3Key)
WHERE id IN (/* ids from falhas */)
  AND active = 1
  AND s3Key NOT LIKE '%/%';

-- 5.3 Verify:
SELECT id, s3Key FROM question_image WHERE id IN (/* ids from falhas */);
SELECT COUNT(*) FROM question_image WHERE active = 1 AND s3Key NOT LIKE '%/%';   -- expect 0
IMPORTANT: apply 5.2 only to ids whose failure is NOT "the object never existed". For each id, confirm
questions/<key> exists in S3 (HEAD) before repointing; a row whose object is missing in both places
would just move the 404 from one key to another (it was already broken). If the response was lost
(504), the candidate set is every row returned by the final COUNT query in 5.3; HEAD-check them first.
Rollback of the whole run (DB side only, together with moving files back in S3):
UPDATE question_image qi JOIN question_image_backup_s3key b ON b.id = qi.id SET qi.s3Key = b.s3Key;

6. RISKS FOUND
- MEDIUM: request outlives proxy timeouts -> lost response (see 4.iii). Data effect is none; operational

- LOW: non-atomic Delete-then-UPDATE; any crash mid-run orphans at most the single in-flight row.
- LOW: un-encoded CopySource (safe for this key set; keys are [A-Za-z0-9._-], max 10 chars).
- INFO: local dump != production; trust the production dry-run.

8. RECOMMENDED CHANGES BEFORE THE RUN (described, NOT implemented)
1) Add an optional `limite` (e.g. 50) to migrar-legadas so the run can be repeated in short batches that
   each finish under 60 s and each return a complete movidos/falhas. The route is already idempotent, so
   repeated calls simply continue. Requires a new deploy of a temporary route, so weigh against (2).
2) Cheaper alternative with no code change: run the POST from the server itself (curl against
   localhost:<port> with a long --max-time and a valid admin token) so nginx/ALB are bypassed and the
   response is received in full; or raise proxy_read_timeout / ALB idle timeout temporarily.
3) Optional: pass ServerSideEncryption/Metadata from the HeadObject in the CopyObject (same as
   aplicarNoCache) to avoid depending on bucket default encryption.
